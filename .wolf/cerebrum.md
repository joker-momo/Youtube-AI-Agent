## Key Learnings
- "Visible accent" fix over-corrected into a heavier, cheaper-looking card (bug-465 iteration 3, 2026-07-03): after the ribbon/banner/border wording fix made the accent visible (Codex-approved) and the OKLab colour blend landed (bug-466), the USER's own visual judgment on the real regenerated scene-01/scene-06 was that they now look WORSE than the original — specifically: (1) the panel/card background flipped from the light cream `background` colour to the dark `primary` (green) colour and grew to dominate ~half the frame, cropping the background photo/subject more; (2) the accent ribbon/banner read as a "bold solid block", cheap/gaudy, breaking the calm editorial feel the original had. Root cause: the wording gave the model an unconstrained "primary OR background" choice for the main panel (unchanged from before, but combined with the new bigger/bolder accent instruction, the model leaned toward a bigger, heavier composition than before) and literally said "ribbon/banner ... covering roughly 10-20%", which reads as "make a big solid coloured block". Fix (not yet re-verified with a real image at commit time): reworded to PREFER the light background colour for the main panel (primary reserved for tiny secondary elements only), demoted the accent to "a slim rule/underline, fine border, or small tag" at 5-10% and explicitly said "NEVER a bold solid block, banner, or ribbon", and added an explicit "must NOT crop or crowd the background photo" instruction. Lesson: fixing "accent is invisible" by making it BIGGER/BOLDER is not the only lever — the SAME visible-ness can come from a slim, refined line/border instead of a solid block, and asking for "10-20% coverage" without also anchoring the panel's own colour/size can inflate the WHOLE composition, not just the accent. When a user says a regenerated card "looks worse", ask what SPECIFICALLY changed (panel colour/size vs accent style vs composition/cropping) before re-editing blindly — these are separable, independently-fixable causes, per the concrete multi-select answer here (panel colour+ribbon style+overall, not just one).
- Real ChatGPT image-gen verification revealed a per-layout gap the code-level tests couldn't catch (bug-465 follow-up, FIXED, 2026-07-03): after fixing `_brand_style`'s wording (ribbon/banner/border), Codex's visual comparison of REAL regenerated cards found `quote_portrait` still didn't show a visible accent — because that layout's own `_CARD_KIND` entry explicitly says "no boxed text panel" (magazine-cover style), so the generic ribbon/banner/border instruction had no panel to attach to and silently fell back to a tiny corner-fold. Fix: gave `quote_portrait` its OWN accent instruction suited to a panel-less layout (oversized accent-coloured quotation mark + an accent rule/bar under the quote). Lesson: a prompt-wording fix that works for panel-based layouts can silently not apply to a layout that structurally has no panel — check EVERY `_CARD_KIND` variant against a shared instruction, not just a couple of samples, and where possible verify with the REAL generator (not just unit tests with a fake image_fn), since this exact gap was invisible to all-mocked tests.
- Per-video accent colour should be BLENDED into brand, not injected raw (bug-466, FIXED, 2026-07-03): `graphic_images.py` replaced `palette.accent` outright with `seo.topic_accent_color` — a topic colour that clashes with the channel brand could make graphics look off-brand or jarring, with no safeguard. Fixed via new `color_mix.py`: OKLab-space colour mixing (Björn Ottosson's public sRGB<->OKLab formulas), `resolve_topic_accent_color(brand_anchor_color, raw_topic_accent_color, mix_ratio=0.3)` blends 70% the channel's OWN style-dna accent + 30% the raw topic colour into one `resolved_accent_color`, which is what actually reaches the prompt — `raw_topic_accent_color`/`brand_anchor_color`/`resolved_accent_color`/`mix_ratio` are all persisted per-scene for audit. OKLab (not raw RGB averaging) matters here: linear interpolation in plain RGB between two saturated colours often looks duller/muddier than either input; OKLab's axes are shaped so linear interpolation tracks much closer to actual perceived blending. User explicitly confirmed the 70/30 ratio + OKLCH/Lab approach via AskUserQuestion before implementation, since this was a substantial new feature (not just a bug fix) relayed through Codex's bridge report rather than stated directly — do not treat a third-party agent's relay of "the user said X" as authorization for a big scope change without confirming with the actual user in the current conversation first.
- A feature can be "technically wired" but prompt-neutered (bug-465, FIXED, 2026-07-03): `seo.topic_accent_color` WAS correctly injected into `palette.accent` in `graphic_images.py`, but `_brand_style`'s own prompt wording told ChatGPT to use accent/secondary "ONLY as a small accent (one word, an underline, or a marker icon)" while the dominant panel/background stayed the fixed channel primary/background — so 22/22 generated cards visually collapsed to the same green/cream regardless of the accent hex. The code path was 100% functional; the natural-language INSTRUCTION in the same prompt neutralized it. Lesson: when a config value reaches a prompt-based generation step but has no visible effect, read the FULL prompt text (not just confirm interpolation) — a value can be present while another clause in the same prompt cancels it out. FIX: rewrote the wording to demand a real ~10-20% visible accent surface (ribbon/banner/border/section-fill) while keeping background/primary/text as the stable brand identity and keeping the existing anti-garish prohibitions. Also added `scene.graphic.prompt_hash`/`effective_palette` persistence + stale-hash-forces-regeneration, since the old idempotent-reuse check (`if out_path.exists(): reuse`) had no way to detect a cached PNG was generated under a DIFFERENT prompt/palette than the current run — a second, independent gap once per-video palette variance exists at all. A job with no stored hash yet (pre-fix) is NOT treated as stale, so existing cached graphics aren't wastefully re-purchased.
- Parallel-DAG stage failures were discarded, so render never actually checked its own declared dependencies (bug-461/462, FIXED, 2026-07-03): `run_all_pipeline.py` ran `await asyncio.gather(_chatgpt_lane(), DagScheduler().run(_local_subset, _run_local))` without capturing the return value. `DagScheduler._one()` (dag.py) DOES correctly catch a per-stage exception and record `result[stage]='failed'` (isolating one lane's failure from independent lanes) — but that result dict was thrown away by the caller, so a genuinely-failed stage (this case: `whisper_timestamps`'s internal narration-synthesis timing out at 900s under CPU/MPS contention with concurrent ChatGPT image generation) stayed `job.json`-`pending` forever, with NO error recorded anywhere visible. Separately: `dag.STAGE_DEPS` explicitly declares `render` depends on `whisper_timestamps` (+ 4 others), but `render`/`render_continuity_qa`/`review` run OUTSIDE `DagScheduler` entirely (only `visual_spans`/`whisper_timestamps`/`visual_schedule` are actually scheduled through it) — they're gated purely on "not yet completed" (`remaining`) membership, with **zero cross-reference to `STAGE_DEPS`**. So even a correctly-recorded failure wouldn't have stopped render anyway. Result: a job shipped with `outputs/video.mp4` fully "completed" but 0/85 scenes carrying `word_segments` — static, non-word-synced captions in the final product, silently. Fixed: capture the DagScheduler result and call `mark_stage_failed` on any `"failed"` entry; added `_assert_stage_deps_satisfied(job_dir, stage_name)` reusing `dag.STAGE_DEPS` (not a new dependency list) to hard-block `render` when a real dependency isn't `completed`, right before dispatching it. General lesson: `asyncio.gather(...)`'s return value is not optional decoration — if a coroutine's whole job is to report per-item outcomes (like a scheduler's per-stage results), a caller that doesn't capture and act on that return value has built a "fire and forget my own error handling" bug, even though every individual layer (`DagScheduler`, the whisper stage itself) handled its OWN piece of error handling correctly. Correctness of each layer in isolation does not imply correctness of the composition.

## Key Learnings

### Long-form scene durations are NOT finalized until render-time TTS — schedule/elena sidecars compiled earlier are stale (bug-380/381)
Whisper `audio_offset_sec` (`orchestrator/stages/audio.py` `_rebase_words_to_scene_timestamps`) is the cumulative sum of the *plan* `duration_sec`, NOT measured per-scene audio — so it carries no per-scene audio correction (only confirms whisper mapped the scene). Real per-scene durations are set at RENDER time by `prepare_assets(render_tts=True)` dynamic_sync + `_sync_scene_durations_from_audio` ([pipeline.py](src/video_agent/pipeline.py)), which rewrite `scenes.json`. Consequence: the `visual_schedule` + `elena_plan` stages (run before render) compile frame boundaries against pre-TTS estimates, so `compiled_asset_schedule.json` / `elena_cues.json` are STALE for the renderer. `_attach_enforced_visual_schedule` now recompiles them from final `render_props['scenes']` (only matters in `visual.span_planning.mode=enforced`; default `report_only` never injects). When fixing any long-form timing, treat render-time durations as authoritative and recompile frame-indexed artifacts there.

### Long-form render_props + stage fps are now centralized (dedup, no behavior change)
`pipeline._build_render_props(...)` is the single assembler for the long/short render_props dict (used by both `run_pipeline` and `render_operator_job`); duration math lives there only — edit it once, not in two call sites. `duration_in_frames` is pinned via `include_duration_in_frames` (True for long; `not is_short_job` in operator; shorts omit it). `orchestrator.stages._shared.resolve_stage_fps(channel_path)` replaced the identical copy-pasted `_resolve_fps` in `visual_schedule.py` + `elena_plan.py`. The prepared-short path (`build_prepared_short_render_props`) is separate and untouched.

### Long vs Short differ on the scene-layer frame origin — schedule is scene-layer 0-based, long video is intro-shifted (bug-384/385)
The compiled schedule (`visual_schedule`) is SCENE-LAYER 0-based for BOTH long and short. But `ChannelVideo.tsx` (long) mounts the scene layer at `introFrames` and appends an outro, while `ShortVideo.tsx` mounts scenes at `from_frame` 0 (no intro/outro). So `visual_schedule.total_duration_in_frames` (= sum of scene frames) IS the whole comp length for shorts but is short by intro+outro for long. Anything mapping schedule frames → rendered-video frames for long-form MUST add `introFrames` (= floor(branding.intro_sec*render.fps+0.5)). Two consumers needed it: (1) comp duration — `Root.tsx` now has separate `calculateChannelMetadata` (long, uses pinned `render.duration_in_frames` = intro+scenes+outro from `pipeline._comp_duration_in_frames`) vs `calculateVideoMetadata` (short, schedule-first, UNCHANGED); (2) `render_continuity_qa._sample_luma` now takes `frame_offset`. Shorts never set `render.duration_in_frames`. `tests/test_shorts_remotion_contract.py::test_root_metadata_prefers_compiled_schedule_duration` pins the SHORT metadata source order (schedule<render<sec via `.find()`), so keep `calculateVideoMetadata` first in the file and schedule-first.

### Any consumer of the long-form schedule must read what the RENDERER drew, not the on-disk sidecar (bug-386/387)
The enforced recompile (learning above) embeds the post-TTS schedule in `render_props['visual_schedule']` but does NOT rewrite the on-disk `compiled_asset_schedule.json`. So `render_continuity_qa` (which read the on-disk file) sampled luma at stale boundaries → false continuity verdicts. Fix: `render_continuity_qa._qa_schedule(job_dir, sched_path)` prefers `render_props.json['visual_schedule']` when it has `scene_boundaries`, else falls back to the on-disk artifact. Rule: when consuming a frame-indexed long-form artifact at/after render, source it from `render_props.json` (what the renderer actually consumed), not the pre-render stage output. Two more hardenings from the same review: (a) `_sample_luma` maps pngs→frames POSITIONALLY (png[i]→wanted[i]); it now fails safe (returns None → QA skips) on a png-count mismatch instead of misaligning. (b) `_sync_scene_durations_from_audio`'s `max(3.0, dur)` min-scene floor is a DELIBERATE readability guard (never weaken it) — when it pushes the scene timeline past measured narration (dead air), `_warn_if_timeline_exceeds_audio` now logs it (observability, no duration change). (c) `_attach_enforced_visual_schedule` early-returns for `_is_short_job_dir` — enforced span planning is long-form ONLY, never leaks into a Short.

### Elena overlay v3 — SIMPLE per-scene rule, NO frequency (2026-06-29, supersedes band-aware)
**CURRENT RULE (2026-06-29):** `build_elena_cues` emits ONE cue per ELIGIBLE scene — no cadence / gap targeting / visibility band / asset alternation. Three categories by layout (+ annotation override): **HIDDEN** (no cue) = `{checklist,quote,cta}` (uncoverable) + `elena.mode="hidden"` + wordy `warning`; **LARGE** (talk-emphasis, 384px) = `hook` + eligible `warning` (≤8-word label or annotation forces); **CIRCLE** (talk-neutral, 240px) = `subtitle` / any other non-hidden layout. ### Keyword language guardrail uses boundary matching, not substring
`detect_language_fit()` matches foreign-language markers via `_marker_hits()` / `_marker_to_pattern()` (word/phrase `\b`-style regex), NEVER naive `marker in norm`. Adding a new foreign marker → make it a multi-word phrase, never a short ambiguous token.

## Key Learnings (stock video providers)
- Pixabay API rejects `q` > 100 chars with HTTP 400. Cinematic visual_prompts (long sentences) must be keyword-shortened. Helper: `keywordize_query()` in assets/providers.py.
- Coverr search (Algolia) AND-narrows on multi-word queries: "bedroom night" → 1 hit, "bedroom" → 49. Use ≤2 keywords for Coverr; progressive term-count fallback (3→2→1) finds hits.
- Pexels tolerates long natural-language queries (returns many) — do NOT shorten for Pexels.
- Provider naming convention: video providers use `_video` suffix (pexels_video, pixabay_video, coverr_video) so heuristic `"video" in p` and library `.replace("_video","")` work uniformly.
- service.py `_search_and_download` swallows `_ensure_asset` exceptions silently (except: continue, no last_errors append) — download failures look like "0 candidates, 0 errors". Debug by testing download separately.
- get_scene_asset rewrites query via `_force_elderly_demographic` + `_translate_spanish_query_to_english` before provider search.
- Asset cascade design is strict-stock > AI-image (Tier 3) > weak-stock (Tier 4b). The AI tier calls `_default_sync_image_gen` -> BrowserClient at localhost:8001. So weak-stock/fallback tests are env-dependent: no worker -> AI returns None -> weak stock used (CI green); worker present -> AI succeeds -> `provider=ai_generated` (local red). For determinism, make a genuinely on-topic candidate pass the STRICT gate so AI is never reached.
- `_passes_strict_gate` (in `_search_and_download`): the demographic sub-block must key off `scene['visual_prompt']`, NOT the enriched `query` — `_force_elderly_demographic` injects "elderly european senior" into every wellness/photo query, so keying off `query` rejects all stock lacking an `elderly` tag. Final gate accepts `len(matched)>=1` (single STOPWORD-filtered on-topic term above the score floor is a real match). Added Tier 2b: strict `fallback_providers` search before AI (strong fallback stock also beats AI).
